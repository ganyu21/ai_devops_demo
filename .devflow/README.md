# 流程产物目录约定

每一条工单在本目录下有一个自己的子目录：`.devflow/issue-<工单号>/`。

这些文件**随分支一起提交**，不是临时产物。它们是流程的可审计轨迹：谁在哪一步做了什么判断、依据是什么、批准记录在哪，事后都能从 git 历史里读出来。

## 目录结构

```
.devflow/issue-<工单号>/
├── 01-requirement/
│   └── change-breakdown.md      需求拆解：六段式
├── 02-dev/
│   └── impl-report.md           实现报告：每条需求的落地情况与自报的未覆盖点
├── 03-hotfix/
│   └── hotfix-report.md         线上缺陷分诊：能否复现、复现方式、缺陷位置、严重级别与依据
├── 04-merge/
│   └── conflict-resolution.md   冲突仲裁：哪些文件冲突、两侧的修复是否都保住了
├── 05-gate/
│   └── cr-checklist.md          准出自查：逐项结论 + 在门禁现场重新核对过的未覆盖点
├── 06-delivery/
│   ├── release-note.md          交付说明：变更点、门禁数字、遗留风险
│   └── issue-comment-<工单号>.md  回写到工单的评论正文
└── state.json                   状态机：当前阶段、门禁批准历史、是否真的合并进 main
```

## `change-breakdown.md` 的六段

| 段 | 放什么 |
| --- | --- |
| **Fact** | 只读勘察得到的事实。工单原文与代码现状不一致时，以哪个为准要写明 |
| **Request** | 要做的事，每条编稳定号 `REQ-NN`，带 `affectedPaths` 与可执行的验收标准 |
| **Constraint** | 不可协商的约束（安全策略、冻结契约、门禁阈值、对外承诺） |
| **Risk** | 已知风险，包括被裁定接受但必须带着走的那些 |
| **Open Question** | 需要人裁定的问题。**不是异常**，是正常的澄清路径 |
| **Conflict** | 需求内部或与现状矛盾的地方，同样交给人裁定 |

`Open Question` 与 `Conflict` 非空时，流程会挂起去问需求提出人。只有「有阻塞且完全没有任何可问人的事项」才直接终止。

## 两条纪律

1. **编号稳定**：`REQ-NN` 不得重排、不得复用废弃编号；分支名的 slug 一旦定了就沿用，否则分支名会漂移。
2. **状态由事实决定**：`state.json` 里的交付状态必须由「合并是否真的核实成功」推导出来，不得无条件写成已交付。合并被治理控制挡住时，状态就是阻塞态，并写明解除路径 —— 虚标成功会让下游所有人都基于一个假事实做决定。

## 续跑

重跑同一条工单时**不该冷启动**：已答复的 Open Question、已裁定的 Conflict 都是需求基线的一部分，重新问一遍等于让需求提出人做第二次同样的决定。判断是冷启动还是续跑，读 `change-breakdown.md` 文档头的「启动方式」段，不要去验收标准里找。

有个陷阱：基线产物提交在 feature 分支上，而上一轮流程可能把 HEAD 留在 `main`（分诊阶段要切 `main` 定位缺陷）。这时产物在工作区里根本不存在，会被误判成冷启动。所以开工前先 `git branch --list 'feature/issue-<工单号>-*'`，有就切过去再核对。
