# 实验手册 · v4 学员版

这一份是**给你动手用的**：阶段任务、产物要求、验收口径、命令速查、纪律红线、评分标准。

**不含参考答案。** 需求裁定的参考口径、缺陷的确切位置、红灯分支的设计意图、未覆盖点的分类答案，都在讲师手里。你自己推出来的结论才算这一轮的产出。

> 一句提醒：本仓早期的提交里留有一版讲师文档（已从当前工作树移除）。去翻它能让这一轮变得毫无意义——而且翻这个动作本身就是个教训：**公开仓里删掉文件不等于删掉内容**。

---

## 1. 你这一轮要交付什么

一张需求 issue 加一张线上问题 issue，在同一个靶仓上并行推进，最后合成一次交付。

- **靶仓**：本仓（`ganyu21/ai_devops_demo`），业务是短链接服务，Java 17 / Spring Boot 3.2.4 / Maven。
- **需求 issue**：两处加固（解析缓存、访问流水）。正文里有 **10 条待澄清问题、1 条已知矛盾、5 条不可协商约束、4 条明确的非目标**。
- **线上问题 issue**：只有症状，没有堆栈、没有行号、没有严重级别。**这三样都要你自己给出来。**
- **你的角色**：人类架构师 / TL。你指挥一支 5 个数字员工的团队，自己不写业务代码。你手上真正的活是**做判断**：裁定需求、守两道门禁、批准准出、审计记忆。

先把两张 issue 从头读到尾。**「明确的非目标」那一节和「约束」那一节，比需求本身更容易让人翻车。**

## 2. 环境与你手上的工具

### 2.1 构建

```bash
export JAVA_HOME=/opt/homebrew/opt/openjdk@21
/opt/homebrew/bin/mvn -B clean verify
```

`JAVA_HOME` **必须显式指定**。不钉死，本地与 CI 会用不同 JDK，跑出两套结果，你会去追一个只存在于一侧的幽灵失败。

### 2.2 GitHub：一律走封装脚本

```bash
GL=./lab/scripts/github-lab.sh
$GL issue <n>                       # 读 issue 正文、标签、状态
$GL pr-status <n>                   # 这条 PR 到底能不能合
$GL commit-status <sha>             # 这个 SHA 上真的回写了哪些状态
$GL ruleset                         # main 上的治理控制现状
$GL push <branch>                   # 推分支（必须走这里，见下）
```

**为什么 `git push` 也要走脚本**：机器上自己的 git credential helper 里存着有 admin 权限的仓主 token，直接 push 就是静默提权、绕过最小权限设计。封装脚本会把 `credential.helper` 置空，改用一张只授权本仓、没有 Administration 权限的受限令牌。

**不要去找那张令牌**。它在仓库外面，在 fileGuard 黑名单上。读不到就是边界，不是障碍——把拿不到的东西如实写进阻塞，然后继续做其余的事。

### 2.3 CI

```bash
JL=~/jenkins-lab/jenkins-lab.sh
LAB_JOB=ai-devops-demo-verify LAB_REPO=$PWD $JL build <分支名>   # 触发并等结论
LAB_JOB=ai-devops-demo-verify LAB_REPO=$PWD $JL console <build号>
LAB_JOB=ai-devops-demo-verify LAB_REPO=$PWD $JL status
```

`build` 的第一个参数是**分支名，不是构建号**。

结论只认两处结构化输出：脚本返回的那行 JSON，以及构建日志里的 `=== GATE SUMMARY ===` 段。**不接受「我跑了一下，应该是绿的」。**

### 2.4 与数字员工团队对话

```bash
QW=~/.qoderwake/qoderwake
CONV=<群会话 id，问讲师要>
$QW messages send $CONV --mention Lead-Waker --intent request_action --text "…"
$QW messages list $CONV --limit 100 --json
$QW runs list $CONV          # 排障第一条：先看 run 状态，不要先看消息列表
```

发消息的写法纪律：`--text` 只放短结论；长内容写成文件用 `--file`。**不要**把带 markdown 标题行（以 `#` 开头）的多行正文塞进 `--text`——那会命中一条 shell 写法守卫，卡进 5 分钟人工审批，而审批只存内存、超时即失败且无法补批。后果是**回复已经写好了却发不出去**，看起来像那个角色没响应。

## 3. 八个阶段：每阶段交什么、怎么算过

产物目录约定见 `.devflow/README.md`。所有长文档写进 `.devflow/issue-<n>/` **并提交进 git**，群里和 issue 里只放结论、路径与下一个责任人。

| 阶段 | 交什么 | 怎么算过 |
| --- | --- | --- |
| **S1 需求拆解** | `01-requirement/change-breakdown.md`，六段式 | 10 条待澄清问题**逐条列出**，一条不漏、不合并、不自行假设答案；矛盾那条单独成段；每条 REQ 有稳定编号、`affectedPaths` 与可判定的验收标准 |
| **G1 人工门禁** | 批准记录持久化 | **你**逐条裁定，裁定要给内容（具体数值、具体接口形态、具体存储选型）。「按推荐的来」不算裁定，会让 S1 原地再问一遍 |
| **S2 实现** | `02-dev/impl-report.md` + feature 分支提交 | 逐条 REQ 的验收标准真落地；「未覆盖点」如实填写，不许写「无」敷衍；**没有违反「明确的非目标」里的任何一条** |
| **S3 缺陷热修** | `03-hotfix/hotfix-report.md` + hotfix 分支 | 能稳定复现（给出复现方式）、`defectSite` 精确到文件与行号、**严重级别由你判定并写清依据**；复现测试留在工作区、保持未跟踪状态交给下一阶段 |
| **S4 冲突仲裁** | `04-merge/conflict-resolution.md` | 逐处记录 ours 语义 / theirs 语义 / decision / rationale；`bothFixesPreserved=true`；仲裁后两侧测试的**并集全绿** |
| **S5 CI 门禁** | `05-ci/heal-round-N.md`（若触发） | 结论有结构化输出支撑；红灯时定位到具体阶段与具体报错行；返修**没有降阈值、没有加 skip 参数** |
| **G2 人工门禁** | `05-gate/cr-checklist.md` | 自查清单逐项有结论；未覆盖点**在门禁现场重新核对过**（不许沿用 S2 的清单）；**你**批准 |
| **S6 交付** | `06-delivery/release-note.md` + issue 回写 + `state.json` | 合并状态**如实**（合并没核实成功就写阻塞态并给解除路径）；遗留风险写进交付文档，不因「已裁定过」而删掉 |
| **P6 独立验收** | QA 的三态结论 | PASS 必须附证据；CHANGES_REQUIRED 必须附可复现的失败与下一个责任人；BLOCKED 必须写清缺什么 |

**判定严重级别时要回答一个问题**：受影响的流量是异常流量，还是**正常流量**？

**未覆盖点要分类**，不要一律「补到 100%」：哪些是真的没被验证过的业务逻辑，哪些是框架入口，哪些是刻意保留的已知未覆盖点。分类要给依据。

## 4. 纪律红线

以下任何一条被触碰，这一轮判不通过，与代码写得好不好无关：

1. **不得让门禁变绿**：调低覆盖率阈值、禁用或排除 JaCoCo / Checkstyle / SpotBugs / Flyway、加 `-DskipTests` / `-Dcheckstyle.skip` 之类参数、用 `--no-verify` 绕过提交钩子。判断标准是一句话——**这个改动是让需求能实现，还是让门禁变绿。**
2. **不得绕过治理控制**：直推 main、force push、用管理员特权合并、改分支规则集、把状态写成已交付而实际没合并。
3. **不得越范围**：issue 正文「明确的非目标」里列的事情一件都不许做。**「顺手修一下」在这套流程里不是好心**——它会让另一条工作线失去证据。
4. **不得改冻结边界**：`openapi.yaml` 里两个已发布路径的既有定义、已合入的 `V1__*.sql`。只允许纯新增。
5. **不得虚报**：结论要能指回结构化输出、源码里真实存在的代码、或 git 历史。「跑过了」不等于「验过了」，「本地绿了」不等于「能合并」。

**被守卫拦下就是边界，不是障碍**：不重试同一条命令，不换写法绕路，把拿不到的东西如实写进阻塞，然后继续做其余的事。

## 5. 评分标准（四维，各 25%）

| 维度 | 达标标准 |
| --- | --- |
| **Waker 与编排配置** | 配出职责互不重叠的角色，能说清**为什么跑门禁的不能是改代码的**；绑定最小化能力与最小权限身份；两道人工门禁建模成流程里的一等节点 |
| **变更与冲突仲裁** | G1 逐条裁定并冻结基线；续跑时不重复提问；真冲突下做到两侧修复都保住，能说清**为什么不能整文件取一边**；没有违反「明确的非目标」 |
| **CI 门禁、治理控制与逆向分诊** | 能读懂构建日志定位到具体断言行；能演示返修且未降阈值、未用 skip；能说清规则集各条挡什么、「管理员也不得绕过」意味着什么、以及**为什么本地门禁绿了还不等于 PR 能合并**；分诊产出含可复现结论、精确位置、**自己判定的**严重级别及依据 |
| **代码质量、治理与记忆** | 门禁达标；**遇到治理控制时如实上报而非绕过**；产出准出报告与 issue 回写；能审计记忆并识别出污染条目；能判断 AI 审查意见里哪几条该采纳、哪几条与范围纪律冲突 |

## 6. 排障：先查什么

按这个顺序查，不要跳步：

1. **消息发出去没人回** → `$QW runs list <convId>`。看 run 是不是 `failed`，错误原因就在那一列。**只看消息列表会误判成路由没通**，然后去改 SOP 的路由段落，那是改错了地方。
2. **角色答得像没读过流程** → 让它逐字引用一句 SOP 正文。引不出来就是正文没物化，要先发预热消息，不是重绑一次就完事。
3. **PR 合不进去** → 先 `$GL pr-status <n>` 看 `mergeStateStatus`，再 `$GL commit-status <head-sha>` 看必需检查在不在。**注意状态绑在 SHA 上，不绑在 PR 上**：批准之后再推一个提交，已有的状态就作废了，关卡会重新落下。
4. **本地绿 CI 红（或反过来）** → 两边的 `JAVA_HOME` 是不是同一个。钉死之后覆盖率应当逐位一致。
5. **门禁红了但 GitHub 上没状态** → 回写桥断了。构建会被标成 UNSTABLE 而不是 FAILURE，这是设计（桥断了是基础设施问题，不该伪装成代码问题），**但没回写成功就等于合不进去**，要如实报成阻塞。
6. **解析 CLI 输出拿到空结果** → 先确认形状：有些命令的 `--json` 返回**顶层数组**而不是 `{data:{…}}`；`--limit` 超过服务端上限会**静默返回空且退出码仍是 0**；有的命令 `--json` 打的是表格，要 `--format json` 才给 JSON。
7. **判断命令成没成** → 别用 `cmd | tail`：管道会掩码前一段的退出码。要判成败就重定向到文件再看。

## 7. 收尾

- 对照第 5 节的四维标准自评，逐条写清证据在哪。
- 打开 `state.json` 的批准历史，确认两道门禁的批准记录都在。
- 审计这一轮沉淀的记忆：哪几条是**可迁移的判断**（该留）、哪几条是**一次性事实**（issue 号、分支名、提交哈希、产物路径——不该进记忆）、哪几条**看起来对但嵌了错前提**（最危险）。
- 确认 `.devflow/` 下的产物全部提交进了 git。**交付产物落在 git / CI / issue 里就是安全的，落在 Agent 平台自己的存储里就要单独备份。**
